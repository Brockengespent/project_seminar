# ПРИЛОЖЕНИЕ А. Техническое задание на разработку backend-сервиса трекера и LLM-консультанта по индивидуальной образовательной траектории в ИТ

## 1. Общие сведения

- **Полное наименование системы:** Backend-сервис трекера и LLM-консультанта по индивидуальной образовательной траектории в ИТ на основе графа навыков с оптимизацией производительности и расхода токенов.
- **Краткое наименование:** Сервис навигации и консультирования ИОТ.
- **Основание для разработки:** Выпускная квалификационная работа бакалавра по направлению подготовки факультета прикладной информатики Университета ИТМО.
- **Исполнитель:** Смирнов Г. В.
- **Научный руководитель:** Говоров А. И., старший преподаватель, факультет прикладной информатики (Университет ИТМО)
- **Плановые сроки разработки:** сентябрь 2026 г. — май 2027 г.

## 2. Назначение и цели создания системы

Система предназначена для автоматизированного сопровождения индивидуальной образовательной траектории (ИОТ) специалистов и обучающихся в области информационных технологий на основе структурированного графа навыков, учёта прогресса, интеграции с существующей моделью данных и интеллектуального консультирования на базе больших языковых моделей (LLM).

**Цели создания системы:**
1. Заменить ручной выбор тем по статичным дорожным картам (схема Proglib, roadmap.sh) детерминированным расчётом следующих шагов обучения с проверкой пререквизитов.
2. Обеспечить программную синхронизацию профиля и прогресса обучающегося с существующей моделью данных через REST API.
3. Предоставить контекстно-зависимые пояснения рекомендаций через LLM-консультанта при ограничении рекомендаций узлами графа навыков для минимизации галлюцинаций.
4. Снизить средний расход токенов и время отклика при обращении к LLM по сравнению с базовым подходом передачи полного контекста в промпт и обеспечить объективный сбор метрик эффективности.

## 3. Характеристика объекта автоматизации

Объектом автоматизации выступает процесс планирования, отслеживания и методического консультирования при прохождении индивидуальной карьерной траектории в ИТ. В текущем состоянии (AS-IS) процесс требует от обучающегося ручного сопоставления собственных навыков со статичной схемой, многократного пересказа контекста в универсальные LLM-чаты и ручной проверки корректности советов. Разрабатываемый backend-сервис автоматизирует хранение графа и прогресса, вычисление очередного шага и оптимизированное взаимодействие с внешними LLM API.

## 4. Требования к системе

### 4.1. Требования к структуре и функционированию системы

Система реализуется в виде модульного backend-приложения со следующими подсистемами:
- подсистема аутентификации, авторизации и ограничения частоты запросов (`REST API & Auth Middleware`);
- подсистема управления графом навыков, профилем, прогрессом и детерминированного обхода (`Tracker & Graph Engine`);
- подсистема интеграции с существующей моделью данных (`External Model Adapter`);
- подсистема LLM-консультирования, оптимизации контекста, кэширования и валидации ответов (`LLM Consultant & Optimizer`);
- подсистема сбора телеметрии и аудита (`Telemetry & Audit Service`).

### 4.2. Функциональные требования

- **ФТ-1.** Хранение и администрирование направленного графа навыков (`SKILL_NODE`, `SKILL_DEPENDENCY`) на базе схемы Proglib и открытых карт roadmap.sh с атрибутами сложности и типом зависимости (`required` / `recommended`).
- **ФТ-2.** Ведение профиля пользователя, установка целевого узла (`LEARNING_GOAL`) и обновление статуса освоения тем (`not_started`, `in_progress`, `done`, `skipped`, `mastery_score`).
- **ФТ-3.** Двусторонняя синхронизация профиля и прогресса с существующей моделью данных по протоколу REST API с журналированием результатов обмена (`EXTERNAL_SYNC_LOG`).
- **ФТ-4.** Детерминированный алгоритмический расчёт следующих доступных шагов траектории с учётом цели, прогресса и выполненных пререквизитов без обращения к LLM.
- **ФТ-5.** Генерация пояснений к рассчитанным шагам и ответов на вопросы обучающегося через внешние API LLM (GigaChat, YandexGPT и др.) с передачей минимального локального подграфа и краткой сводки прогресса.
- **ФТ-6.** Пост-валидация ответов LLM по списку допустимых идентификаторов узлов графа навыков для исключения галлюцинаций и несогласованных рекомендаций.
- **ФТ-7.** Оптимизация обращений к LLM за счёт кэширования ответов в Redis и реляционной БД (`LLM_CACHE`), сжатия контекста и маршрутизации запросов между моделями разной сложности.
- **ФТ-8.** Регистрация телеметрии по каждому запросу (`REQUEST_TELEMETRY_LOG`): входные и выходные токены, время отклика (`latency_ms`), признак попадания в кэш (`cache_hit`), доля согласованных с графом ссылок (`graph_aligned_ratio`) и признак резервного режима (`fallback_triggered`).

### 4.3. Нефункциональные требования

- **НФТ-1 (Экономичность по токенам):** средний расход входных токенов в оптимизированном режиме должен быть ниже базового режима (передача полного контекста) не менее чем на 50 % при промахе кэша и составлять 0 токенов при попадании в кэш.
- **НФТ-2 (Производительность):** локальный расчёт следующего шага по графу в SQL БД — без сетевого ожидания LLM; медианное время отклика консультанта в оптимизированном режиме ниже базового.
- **НФТ-3 (Достоверность):** доля рекомендаций, согласованных с узлами и пререквизитами графа (`graph_aligned_ratio`), не ниже 95 %.
- **НФТ-4 (Безопасность):** JWT-аутентификация, ролевая модель доступа (`learner` / `admin`), изоляция данных пользователей по `user_id`, rate limiting, хранение секретов и API-ключей исключительно в переменных окружения.
- **НФТ-5 (Отказоустойчивость и наблюдаемость):** сохранение работоспособности трекера и выдача резервного пояснения из БД при таймауте или ошибке 5xx внешнего LLM API; структурированное журналирование ошибок и телеметрии.
- **НФТ-6 (Технологическая совместимость):** реализация на Python 3.12+, Django / DRF, PostgreSQL, Redis с унифицированным адаптером LLM-провайдеров и документированным OpenAPI 3.0.

## 6. Порядок контроля и приёмки системы

Приёмка системы выполняется на основании следующих видов проверок:
1. **Модульное и интеграционное тестирование** (`pytest`): проверка алгоритма обхода графа, RBAC-ограничений, валидации узлов, кэширования и резервного сценария при эмуляции отказа LLM API.
2. **Сравнительный эксперимент (бенчмарк):** прогон серии запросов на синтетических профилях пользователей в базовом и оптимизированном режимах с фиксацией среднего расхода токенов, времени отклика (p50/p95), доли попаданий в кэш и доли согласованных рекомендаций.
3. **Демонстрация и пилотное тестирование:** проверка сквозных пользовательских сценариев через REST API / Swagger UI и анализ экспертной оценки качества пояснений.
